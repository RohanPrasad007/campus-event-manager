[A8] SCOPE: Why a const declared inside a function cannot be seen outside it:
--------------------------------------------------------------------------------
In JavaScript, variables declared with `const` or `let` possess block scope and
function scope. When a function is invoked, the JavaScript engine creates a new
execution context and lexical environment for that function. A `const` declared
within this block is bound strictly to that local environment. Once the function
finishes execution, its local scope is popped off the call stack. Code executing
in the outer or global scope has no visibility into or reference to the inner
environment, preventing accidental naming collisions and memory leaks.

[B5] EVENT BUBBLING: Explanation of how it works and why it matters:
--------------------------------------------------------------------------------
When a user interacts with a page (e.g. clicking an RSVP button), the event travels
in three phases:
1. Capturing Phase: The event trickles down from the window/document to the target.
2. Target Phase: The event reaches the target element (event.target).
3. Bubbling Phase: The event triggers on the target, then bubbles straight up
   through each ancestor element in the DOM hierarchy:
   button -> article -> li -> ul -> div -> section -> main -> body -> document.

Event bubbling enables "Event Delegation": instead of attaching separate click
event listeners to dozens of individual card buttons (which degrades performance),
we attach a single click listener to the parent <ul> container. Inside the listener,
`event.target` identifies the precise element clicked, and `.closest(".rsvp-button")`
captures the exact button clicked.

[B8] VALIDATION: Why the server must still re-check all submitted data:
--------------------------------------------------------------------------------
Client-side validation (HTML constraints like required, pattern, and JavaScript
setCustomValidity) is designed exclusively for user experience: it provides instant,
responsive feedback and saves unnecessary network roundtrips.
However, client-side validation provides ZERO security:
1. A user can disable JavaScript in their browser with one click.
2. Form attributes and validation rules can be modified or deleted in DevTools.
3. Requests can be sent directly to the backend API without using a browser at all
   (via curl, Postman, scripts, or automated bots).
Therefore, the server must always perform strict, authoritative re-validation and
sanitization of all incoming data before processing or storing it.

[JSON/XML A4] ELEMENT VS ATTRIBUTE JUSTIFICATION:
--------------------------------------------------------------------------------
In events.xml:
- `id` is an attribute: <event id="tech-fest">
  Justification: `id` is unique identification metadata about the entity rather
  than human-facing content. Attributes are ideal for identifiers and classifiers.
- `title`, `date`, `time`, `venue`, `seats`, `online`, `description` are elements:
  Justification: These are the actual informational content of the event. Elements
  are readable, can contain multi-line text, support child sub-elements if expanded
  later, and preserve semantic data boundaries cleanly.

[JSON/XML A5] DATES AND TYPES IN JSON & XML:
--------------------------------------------------------------------------------
Neither JSON nor XML supports a native "Date" primitive:
- In XML, everything is stored purely as text (string values) with no native data
  types for numbers, booleans, or dates.
- In JSON, numbers, booleans, strings, arrays, and objects are supported, but there
  is no built-in Date type.
Convention Used:
We store all dates using the ISO-8601 format: `YYYY-MM-DD` (e.g., `2026-09-12`).
Why it is unambiguous worldwide:
ISO-8601 orders units hierarchically from largest to smallest (Year-Month-Day).
This prevents cultural ambiguity (e.g. 05-06 meaning May 6th vs June 5th) and ensures
dates sort chronologically in natural alphabetical/lexicographical order.

Exact Validator Error:

"SyntaxError: Expected double-quoted property name in JSON at position 2831"

Resolution:
Deleted the trailing comma after `false`. In JSON, commas are strictly separators
between items, not terminators; trailing commas are invalid syntax.

[JSON/XML C2] THREE SCHEMA VALIDATION RULES:
--------------------------------------------------------------------------------
1. Rule 1 (Title): `title` must be a non-empty string with length between 2 and 100 characters.
2. Rule 2 (Identifier): `id` must be present, unique across all events, and contain only
   lowercase alphanumeric characters and hyphens.
3. Rule 3 (Date): `date` must conform to the ISO-8601 standard (`YYYY-MM-DD`) representing
   a valid calendar date.

Why validating first matters:
Untrusted or malformed data can crash frontend scripts, cause silent rendering bugs,
or break logical control flow (e.g. if `seats` is a string instead of a number,
comparisons like `seats === 0` or `seats < 5` fail). Validating data before usage
guarantees system resilience and data integrity.

[JSON/XML C3] FORMAT DECISION & REAL-WORLD COMPARISON:
--------------------------------------------------------------------------------
Format Chosen for our Event Board: JSON
Justification:
1. Native JavaScript compatibility: Parsed directly into native objects with
   JSON.parse() or response.json() without manual DOM traversal.
2. Compact & Lightweight: No duplicate closing tags, resulting in significantly
   smaller file sizes (2832 bytes for JSON vs 2951 bytes for XML).
3. Universal standard: JSON is the standard interchange format for modern REST
   APIs and web applications.

Real Scenario where XML is the Better Choice:
Enterprise banking and financial clearing systems (e.g., SWIFT and ISO 20022 message
standards) and SOAP web services. In these environments, XML's formal XML Schema
Definition (XSD), XML namespaces, and cryptographic XML Digital Signatures (XMLDSig)
are mandatory requirements for auditability, contract validation, and legacy system
interoperability.
